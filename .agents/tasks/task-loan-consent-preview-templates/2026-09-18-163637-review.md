# Loaner & guarantor consent preview templates, plus the 4 tokens they lean on (v1)

Re-seeds the two `consent_page_templates` rows the public consent preview page renders (`loaner_consent`, `guarantor_consent`) with the committee's authoritative bilingual (Hindi + English) legal text, and adds the four placeholder tokens that text references — `LOAN_CONSENT_DATETIME` / `LOAN_STATUS` (loan-level, from the loaner consent row) and `CONSENT_DATETIME` / `CONSENT_STATUS` (per-consent, from the document's own consent). Because the committee reset the templates DB, the migration is written to establish the correct current text from any prior state rather than to patch a known one: it DELETEs by `type` then INSERTs, since there is no UNIQUE index on `type` to hang an `ON CONFLICT` on. The placeholder change threads through the existing single-source-of-truth builder so the consent page, Bulk Generate, and Download Center all resolve the new tokens identically. No frontend files change; the existing Accept / declaration-tick / Decline controls are untouched.

Watch for: nothing blocking. The one thing worth a conscious glance (all **confirmed**) is that the seeded bodies embed intentional oddities from the source text — a stray backtick in guarantor §4.1 and literal `[ ACCEPT … ]` / `[ DECLINE … ]` / `☐` display markers — that are deliberately preserved and must not be "cleaned up" in a later edit, because they are the committee's verbatim content and the markers are inert (they carry spaces, so the `[A-Z0-9_]+` substitution regex never touches them).

**Verdict**: APPROVED

## High-level view

The migration targets `chhath-templates` and is self-healing: DELETE-by-type then INSERT means re-running from a stale, duplicated, or empty state converges to exactly one row per type. `updated_at` is a fixed ISO literal, not `datetime('now')`, so the file checksum is stable and re-application is a genuine no-op on content. No `BEGIN/COMMIT/SAVEPOINT`, which D1 rejects in `--file` scripts.

The seeded text is byte-for-byte identical to the two provided fixtures (loaner 8831 chars, guarantor 7376 chars after newline normalization) — independently re-verified here by applying the migration into an in-memory SQLite and diffing against the fixtures. Apostrophes in `guarantor's` / `committee's` / `Loaner's` are correctly SQL-escaped as `''`, and the source's stray backtick and declaration/action markers survive verbatim.

The four new tokens are wired to real `loan_consents` data through the shared `consentPlaceholders.js`, which exists precisely because two placeholder maps once drifted. The loaner body uses the loan-level `[LOAN_STATUS]` / `[LOAN_CONSENT_DATETIME]` for its final record; the guarantor body uses the per-consent `[CONSENT_STATUS]` / `[CONSENT_DATETIME]` for that guarantor's own decision — the right split on each side. The factory used by bulk paths overrides the per-consent pair per target while leaving the loan-level pair from the shared base, and a test pins that the two builders never disagree.

The render path is the correct one: `getConsentByToken` pulls `loaner_consent` / `guarantor_consent` from `getConsentPageTemplate`, not the `consent_personal_*` WhatsApp message templates. The frontend consent route is unchanged, so the hard-coded checkbox + OTP + Accept/Decline flow is intact; the in-body markers render as plain text.

### DELETE-then-INSERT as the reset-safe seed

With no UNIQUE index on `consent_page_templates.type`, an upsert isn't available, so each type is reset by `DELETE FROM … WHERE type = 'loaner_consent'` immediately followed by the INSERT. This is what makes the migration valid against the "the DB was reset" premise in the task: it doesn't assume a row exists, doesn't assume only one exists, and doesn't assume the text is any particular prior value. The self-healing test seeds two junk `loaner_consent` rows with wrong text and asserts the migration collapses them to a single row whose body no longer contains the junk — so the convergence property is actually exercised, not just asserted structurally. `updated_at` being a frozen ISO literal (rather than `datetime('now')`) is what lets a second application produce an identical row; the idempotency test applies twice and compares the stored text on both types.

### Text fidelity to the provided fixtures

The dominant risk in a "seed the exact legal text" change is silent corruption — a smart-quote, a dropped line, a mis-escaped apostrophe. Applying the committed migration into in-memory SQLite and diffing the stored `text` against `template-loaner_consent.txt` / `template-guarantor_consent.txt` yields an exact match on both (8831 / 7376 chars). The SQL-level apostrophe escaping (`guarantor''s`, `committee''s`, `Loaner''s`) round-trips back to single apostrophes in the stored value, and the stray backtick in guarantor §4.1 (`\`[MINIMUM_TENURE_MONTHS] months.`) is present in the stored body exactly as in the fixture. The migration test additionally guards that every `[A-Z0-9_]+` token in each seeded body is a key `buildConsentPlaceholders` actually emits, so no token can silently degrade into literal brackets on the live page.

### Token split: loan-level vs per-consent

```
loaner_consent body   → [LOAN_STATUS]      [LOAN_CONSENT_DATETIME]   (+ GUARANTOR_n_*, counts)
guarantor_consent body→ [CONSENT_STATUS]   [CONSENT_DATETIME]        (per this guarantor)
```

`datetimeOf(c)` returns `responded_at || created_at`, so a consent that hasn't been decided yet still shows a sensible timestamp (its creation), and `statusLabel` carries the full verification/decline remark suffixes on both paths. In `buildConsentPlaceholders`, `LOAN_*` derive from the discovered `loanerConsent` and `CONSENT_*` from the passed `targetConsent`; the factory's base is built with `targetConsent = null` (so base `CONSENT_*` are blank) and then each returned closure fills `CONSENT_DATETIME` / `CONSENT_STATUS` from its own target while `LOAN_*` stay as computed loan-level values. Test C constructs both a direct call and a factory closure for the same target and asserts all four match, then feeds a second target to confirm the per-consent pair actually varies — meaning the "no drift" invariant this module exists to protect is pinned for the new fields too.

### Inert display markers vs the substitution regex

The frontend substitutes with `text.replace(/\[([A-Z0-9_]+)\]/g, …)` and returns the match unchanged for unknown keys. `[ ACCEPT & CONFIRM LOAN ]`, `[ ACCEPT CONSENT ]`, `[ DECLINE CONSENT ]` and `☐` all contain spaces or non-ASCII, so none match the token pattern; they render as literal display text after `marked` + DOMPurify. The real controls remain the page's existing checkbox + OTP + Accept/Decline buttons, and no frontend file is in the diff — so the claim that no second UI was introduced holds by construction.

### Migration guard compliance

The new file is registered in `migration-matrix.test.mjs` as `{ schema: 'templates.sql' }`, and `migration-target-databases.test.mjs` scans every migration's `wrangler d1 execute <db>` line against the real D1 names in `wrangler.toml` — the file names `chhath-templates`, which is present (wrangler.toml:175). The migration test also asserts no leading `BEGIN/COMMIT/SAVEPOINT/ROLLBACK` statements survive the comment filter. Full suite: 1112 pass / 0 fail.

### Test meaningfulness

Both new suites are prove-first. `consent-placeholders.test.mjs` asserts concrete values (`LOAN_CONSENT_DATETIME === '2026-10-20T10:00:00.000Z'`, `CONSENT_STATUS` matches `/Declined/` and `/busy/`, `created_at` fallback when `responded_at` is blank) that fail the instant a token is removed or mis-sourced. `consent-templates-migration.test.mjs` applies the real committed SQL against the real `templates.sql` schema and checks row counts, idempotency, self-healing, and token-known-ness. Reverting either change fails these tests.

Not tested: no assertion pins the seeded body to the fixture files byte-for-byte inside the suite — the migration test checks headers, a sample of tokens, and the markers, but a subtle text regression (e.g. a dropped middle paragraph that still keeps the headers and tokens) would not be caught by the automated suite. It was caught here only by the manual fixture diff.

### Scope

Confined to the two features, their tests, and the task-planning artifacts under `.agents/tasks/…` — no unrelated production code bundled in.
