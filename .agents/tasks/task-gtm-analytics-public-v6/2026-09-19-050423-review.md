# GTM container install for public-v6, with SPA page-view tracking and CSP allowances

The public portal's GA4, Clarity, and GTM dashboards were all empty because no analytics of any kind was present in `Public/frontend-v6/src` — no dataLayer, no gtm.js, no clarity snippet. Since GA4 and Clarity are configured as tags *inside* a single GTM container (`GTM-N6BF7NP7`), installing that one container snippet is the correct and complete fix for all three. The change drops the standard GTM loader into `app.html`'s head, adds the `<noscript>` fallback iframe after `<body>`, wires an `afterNavigate` hook so SPA route changes push their own `page_view` (a plain document-load-only install would miss every client-side navigation), and widens the strict CSP so gtm.js/GA/Clarity hosts are not blocked — the same class of block that PR #405 hit with Cloudflare Insights.

Watch for: the custom `page_view` event pushed on every navigation will double-count with GA4's own automatic page_view unless the GTM container is configured to disable GA4's built-in pageview and fire only on this event — a container-side config dependency the code cannot enforce (likely). Clarity may also need a `worker-src`/`frame-src` allowance for `*.clarity.ms` that the current CSP does not grant (possible).

**Verdict**: APPROVED

## High-level view

GTM's async loader sits high in the head and initializes `dataLayer` before the app boots; the `<noscript>` iframe covers the scriptless case. Because GA4 and Clarity are container tags, one snippet legitimately lights up all three dashboards, and no separate GA/Clarity code is needed. The completeness of the fix therefore depends on the container hosting those tags — which the diff can't verify.

SPA page views come from an `afterNavigate` callback calling the browser-guarded `pushPageView`. The open question is not whether the event fires but whether GTM consumes it without also firing GA4's automatic pageview (double-count), and whether a GTM variable maps the custom `page_path`/`page_title` keys onto GA4's expected fields — both dashboard-side config the code can't enforce.

The CSP preserves every prior directive and host byte-for-byte (both Cloudflare Insights hosts included) and adds a genuinely new `frame-src` so the noscript iframe isn't caught by the `default-src 'self'` fallback. Worth checking against Clarity's runtime: it may open a web worker or iframe under `*.clarity.ms`, which the current `worker-src`/`frame-src` do not cover.

The source scan and jsdom unit test lock the install and CSP in place, but the container-side trigger/tag config — where the double-count and field-mapping risks live — is not reachable by any source-level test.

<summary>Issues (3)</summary>

1. **GA4 pageview double-count** — the custom `page_view` event will be counted alongside GA4's automatic pageview unless the GTM container disables the built-in pageview and fires GA4 only on this event. Verify the container config; code alone can't guarantee it.
2. **Clarity worker/frame CSP** — Clarity can spawn a web worker and/or iframe under `*.clarity.ms`; `worker-src` is still `'self'` only and `frame-src` lists only googletagmanager. Confirm against a live load and add `*.clarity.ms` to `worker-src`/`frame-src` if Clarity's console shows a CSP violation.
3. **`page_view` naming may miss GA4 defaults** — `page_path`/`page_title` are custom keys; GA4's built-in page_view expects `page_location`/`page_title`/`page_referrer`. A GTM tag must map these, or the SPA pageviews will land without a proper page path in GA4 (likely).

### One container snippet drives all three dashboards

The head snippet is placed high in the head (after the viewport meta, before the no-flash theme script), so `dataLayer` exists before the app boots and nothing racing to push to it beats the loader. Hardcoding the id is the only option here — `app.html` is a static template with no access to Vite env. Since GA4 and Clarity are tags inside this container rather than separate scripts, the diff correctly contains no GA/Clarity snippet of its own; the fix's completeness rides on the container being configured to host those tags, which the diff can't verify.

### SPA page views and the GA4 double-count risk

```
afterNavigate ──▶ pushPageView(path+search, document.title)
                     │  guards: typeof window, Array.isArray(dataLayer)
                     ▼
                 window.dataLayer.push({ event:'page_view', page_path, page_title })
                     │
                     ▼  (GTM container: trigger on custom event 'page_view')
                 GA4 tag / Clarity tag
```

`afterNavigate` fires on the initial navigation *and* every client-side route change, so the SPA is no longer invisible to analytics after first load.

Two behavioral caveats sit at the GTM/GA4 boundary, not in this code. First, GA4's config tag emits an automatic page_view on load; if the container also fires a GA4 event on this custom `page_view`, the initial navigation is counted twice — the container must disable GA4's built-in pageview or scope the trigger to exclude the first load. Second, the event carries `page_path`/`page_title`, but GA4's page_view semantics key off `page_location`/`page_referrer`/`page_title`; without a GTM variable mapping, GA4 records these pageviews with no well-formed path. Both are container-config dependencies — the code side is correct but is only half the loop.

### CSP widened without dropping anything

Directive-by-directive comparison against `main` confirms no existing host was removed and no directive dropped. `script-src` gains googletagmanager + `www.clarity.ms` + `*.clarity.ms`; `connect-src` gains the GA4 collect hosts, `*.analytics.google.com`, googletagmanager, `*.clarity.ms`, and `c.bing.com`; `img-src` gains GA4 and `*.clarity.ms` pixel hosts. A brand-new `frame-src https://www.googletagmanager.com` directive is added — necessary because none existed, so the noscript iframe would otherwise fall back to `default-src 'self'` and be blocked. `object-src 'none'`, `base-uri`, `frame-ancestors`, `form-action`, and both Cloudflare Insights hosts are byte-identical, and no `comment`/non-schema key was reintroduced into `vercel.json`.

One residual gap worth verifying against a live load: Microsoft Clarity's runtime can spin up a web worker and, in some configurations, an iframe on a `*.clarity.ms` subdomain. `worker-src` is still `'self'` only, and `frame-src` lists only googletagmanager. If Clarity's session recording trips a `worker-src`/`frame-src` violation in the browser console, those directives need `*.clarity.ms` added. This doesn't block the GTM/GA path, only potentially Clarity's recorder.

### Test coverage

The source-scan test (`gtm.test.ts`) asserts the container id appears in both the head snippet and the noscript iframe, that the iframe sits between `<body>` and `%sveltekit.body%`, that the no-flash theme script and sveltekit placeholders survive, and that the CSP carries the right hosts in the right directives with the hardening directives and Cloudflare hosts intact. The helper's jsdom unit test covers the push shape and both no-op branches (absent and non-array dataLayer).

Not tested — and not testable at the source level — is the GTM container's trigger/tag configuration, which is where the double-count and GA4 field-mapping risks live. The tests prove the snippet ships and the CSP allows the traffic; they can't prove the dashboards populate correctly.
