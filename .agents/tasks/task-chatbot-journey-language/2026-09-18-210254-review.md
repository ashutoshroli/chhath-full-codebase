# Journey/decade context section and single-language directive for the public chatbot (v1 review)

Two behavioral gaps in the public AI chatbot's system-prompt builders (`mgmt/server-render/src/lib/publicData.js`) are closed here. First, a bounded "JOURNEY / 10-YEAR STORY" section is appended to all three context builders so a visitor asking about "hamari yatra" / the decade / "since 2017" gets a data-grounded answer instead of the model improvising — sourced cache-only from the already-fetched `portalData` (real `journeyEntries`/`journeyTagline` titles when present, plus always-available derived decade figures). Second, the old single hard-coded Hindi append line is replaced with a `lang`-parameterized anti-gibberish directive threaded through `buildContextForProvider`, telling fallback models to stay in one language and never mix scripts. The suite is green at 217 pass / 0 fail (203 baseline + 14 new).

Watch for: the derived journey grand total sums **all** non-resold rows' `Amount`, but the public "Our Journey" page it claims to mirror counts **money-only** rows (material/service = ₹0) — the two figures diverge whenever material/service rows carry an Amount (**likely**). The chatbot's decade span ends at `max(2017, latestDataYear)`, but the frontend ends at `max(2017, dataMax, currentYear)` — off-by-a-year span and grand total when data lags the calendar year (**confirmed**). The new per-year journey total (resold-excluded) also contradicts the pre-existing "Year Y: collections" line (resold-included) sitting a few lines above it in the same prompt (**confirmed**).

**Verdict**: NEEDS_CHANGES

## High-level view

The journey section is a pure additive helper (`buildJourneySection`) appended after the core sections in `summarizePortalData` and `buildFullContext`, with a one-line variant (`buildJourneyContextLine`) on the year-scoped path. It is cache-only (reads only `data.collections`/`journeyEntries`/`journeyTagline`, never fetches) and bounded (title-only digest, ~6/12-year growth window, appended last so it trims first under the caps).

The correctness problem is in the derived figures. The task's premise is that these numbers "mirror `derive.ts` decadeStats" so the chatbot and the public page agree. They don't, in three ways: money-only vs all-amount totals, the `endYear` formula omitting `currentYear`, and the year source (collections-only vs collections+loans+committee). Each produces a chatbot number that can differ from what the same visitor sees on the "Our Journey" page — the exact failure the feature was meant to prevent. None of the three is exercised by the tests because the fixture uses only money rows and years ≤ a static max.

The language directive is a clean, correct parameterization: `languageDirective(lang)` returns distinct Hindi/Devanagari and English variants, both forbidding script-mixing, appended in addition to (not replacing) the `NO_DEV_INSTRUCTIONS_LINE` guardrail. dataMode selection and the function signature are preserved. No concern here beyond one small asymmetry noted below.

### Derived decade figures don't mirror decadeStats

The task explicitly frames the derived figures as mirroring `Public/frontend-v6/src/lib/api/derive.ts` `decadeStats()` so the chatbot's decade numbers line up "exactly with the public 'Our Journey' page." Reading both, they diverge in three ways, all of which produce a chatbot figure that can disagree with what a visitor sees on the page.

**Money-only vs all-amount (likely).** The frontend's per-year total comes from `computeSummary`, which sums `contributor.amount`, and in `contributorsForYear` `amount` is `isMoney ? parseAmt(c.Amount) : 0` — material (Contribution Type `2`) and service (`3`) rows contribute **zero** to `totalCollected`. The chatbot instead does:

```js
if (truthyResell(c['Is Resell'])) continue;
total += num(c.Amount);              // every non-resold row, regardless of type
```

So any material/service row that happens to carry an `Amount` inflates the chatbot's per-year total, `grandTotal`, and possibly the best-year pick, above the public page's figure. The contributor **count** side actually matches the frontend (both count any non-resold row with an ID, keyed once per person), so only the money totals drift. The fix is to exclude non-money rows from the `total`/`grandTotal` sum, mirroring `computeSummary`.

**endYear omits currentYear (confirmed).** The chatbot computes `endYear = Math.max(DECADE_START_YEAR, latestDataYear)`. The frontend computes `endYear = Math.max(DECADE_START_YEAR, dataMax, currentYear)` and its `DecadeYearStat` explicitly carries an `isCurrent` open year. When the cached data hasn't yet gained a row for the current calendar year, the chatbot reports a span ending one year earlier than the public page, and (because the loop runs `startYear..endYear`) omits the current year's zero-row from `years` — a different span string and a different `grandContributors` denominator than the page shows.

**Year source (confirmed, minor).** `latestDataYear` is taken from `data.collections` only; the frontend's `availableYears` unions `collections`, `loans`, and `committee`. A year present only in loans/committee (e.g. a committee recorded before the first collection of a new year) extends the frontend's span but not the chatbot's.

None of these surfaces in the tests: `JOURNEY_SAMPLE` uses only money rows and a fixed latest year of 2024, so the money-only and current-year paths are never entered.

### Two different totals for the same year in one prompt

Independent of the frontend mirroring, the journey section introduces a figure that contradicts a line already in the same prompt. The pre-existing general-path loop emits, for each recent year:

```js
const totalCol = cols.reduce((s, c) => s + num(c.Amount), 0);   // includes resold rows
lines.push(`Year ${y}: collections ${inr(totalCol)} from ${cols.length} entries; ...`);
```

That total **includes** resold rows (there is a standing note that resold amounts are already counted in the year's collections total). The new journey block then emits, for the same years:

```
Recent years: 2024: ₹3,000 (1 contributors); ...   // resold EXCLUDED
```

For a year with any resold row the two lines disagree on the year's collection total within a single system prompt. The model is now handed ₹3,500 ("Year 2024: collections") and ₹3,000 ("Recent years: 2024") for the same year and left to reconcile them — exactly the kind of ambiguity that produces confident-but-wrong answers. Aligning the journey line to the money-only figure (issue 1) narrows but does not fully remove this unless the pre-existing line's resold-inclusive total is also acknowledged; a one-clause label on the journey line ("resold items and material/service excluded") would disambiguate.

### Language directive asymmetry

`languageDirective(lang)` is correctly parameterized (Hindi/Devanagari vs English, both forbidding script-mixing, appended alongside the preserved `NO_DEV_INSTRUCTIONS_LINE`, signature and dataMode routing untouched). One asymmetry, not a blocker: the Hindi variant names the four offending scripts explicitly ("no Korean, Japanese, Chinese, or Spanish characters") while the English variant only says "any other language or script." The empirical gibberish (mistral-nemotron mixing CJK/Spanish) that motivated FEAT-002 can occur regardless of the requested language, so the English directive would be marginally stronger with the same explicit list.
