# Money-only journey totals and current-year decade span (v2 review)

The v1 review returned NEEDS_CHANGES on three confirmed/likely issues in the public chatbot's journey context builders (`mgmt/server-render/src/lib/publicData.js`): the derived decade totals summed all non-resold rows instead of money-only rows, the span's `endYear` omitted the current calendar year and drew its latest year from collections alone, and a new per-year journey line contradicted a pre-existing resold-inclusive "Year Y: collections" line in the same prompt. Commit `429531b` addresses all three by extracting `isMoneyContribution`, `isResoldRow`, `latestJourneyYear`, and a shared `journeyYearFigures`, then rewiring both `buildJourneySection` and `buildJourneyContextLine` through them, and labelling the journey figures money-only. The changes mirror `derive.ts` (`contributorsForYear`, `availableYears`, `decadeStats`) faithfully, including the default-money-when-`Contribution Type`-absent behavior. Suite is green at 221 pass / 0 fail with two new prove-first fixtures.

Watch for: nothing blocking. One residual, already accepted in v1 as label-only: the money-only "Recent years" line and the resold-inclusive "Year Y: collections" line still report different magnitudes for the same year in one prompt, now distinguished only by their labels (**confirmed**, non-blocking).

**Verdict**: APPROVED

## High-level view

The three v1 fixes converge on one goal — make the chatbot's decade numbers agree with the public "Our Journey" page. The money-only fix now filters the `total`/`grandTotal` sums through `isMoneyContribution`, which returns true for `Contribution Type` `'1'` or `''` and defaults a missing type to `'1'` (money) — a byte-for-byte match with `contributorsForYear`'s `isMoney`. Material and service Amounts contribute ₹0. The contributor count side is deliberately unchanged and still matches the frontend (any non-resold row with an ID, counted once).

The span fix sets `endYear = max(2017, latestDataYear, currentYear)`, matching `decadeStats`, and `latestJourneyYear` unions collections, loans, and committee `Year` values, matching `availableYears`. A stale-data cache now reports a span reaching the present rather than stopping at the newest stored row.

The conflicting-totals fix is label-only, as the v1 review proposed: the journey lines are now tagged "money contributions only; resold items and material/service excluded", so the model can tell them apart from the resold-inclusive year lines. The two figures still differ numerically for years containing resold or material/service rows, but they are no longer two unlabelled totals for the same year.

As a bonus alignment, the new `isResoldRow` broadened the chatbot's resold test from `'TRUE' || true` to also accept `'true'/'1'/'yes'`, exactly matching `derive.ts`'s `truthyResell` — closing a latent mismatch the v1 review did not flag.

### Money-only totals now mirror contributorsForYear

`journeyYearFigures` sums `num(c.Amount)` only when `isMoneyContribution(c)` holds, where that helper is `((c['Contribution Type']) ?? '1').toString()` tested against `'1'` and `''`. This reproduces `contributorsForYear`'s `const cType = (c['Contribution Type'] ?? '1').toString(); const isMoney = cType === '1' || cType === '';` including the default-to-money-when-absent branch, so a row with no type is counted as money on both sides. The `JOURNEY_MIXED_TYPES` fixture proves it: a ₹1,000 money row alongside a ₹10,000 material row and a ₹7,000 service row in 2018 yields a journey grand total of ₹1,000 (not ₹18,000/₹17,000), while all three people still register as contributor entries — the count side reads any non-resold row with an ID regardless of type, matching the frontend's person list.

### Span reaches the current year and unions loans/committee

`endYear = Math.max(DECADE_START_YEAR, latestDataYear, new Date().getFullYear())` matches `decadeStats`'s `Math.max(DECADE_START_YEAR, dataMax, currentYear)`, and `latestJourneyYear` scans collections, loans, and committee just as `availableYears` unions the same three. `JOURNEY_STALE_DATA` (collections 2020, loans+committee 2021) proves the span ends at the current calendar year rather than 2020 or 2021 when "now" is later. The tests compute the expected span end dynamically from `new Date().getFullYear()`, so they won't rot as the calendar advances — the four pre-existing journey tests were updated the same way.

One difference from `decadeStats` remains by design: `decadeStats` falls back to `currentYear` for `dataMax` when no year is present, whereas `buildJourneySection` returns early with an empty section when there is neither data nor story rows. That early return predates this commit and is correct for a context builder — a decade skeleton with no data would be noise.

### Conflicting per-year totals: disambiguated by label

The pre-existing general-path line at lines 144/358/517 still sums every row's `num(c.Amount)` (resold and material/service included) into `Year ${y}: collections …`. The journey block now emits `Recent years (money contributions only; resold items and material/service excluded): …` and the year-scoped line appends `(money contributions only)`. This is the label-only reconciliation the v1 review explicitly offered as sufficient. The residual is real but bounded: for a year with resold or non-money rows the two totals still differ in value; a reader (or model) now has the labels to reconcile them rather than two bare numbers. Fully unifying would require re-scoping the pre-existing resold-inclusive line, which is out of scope for this fix and would change long-standing behavior.

### No regression in unchanged paths

`buildContextForProvider`'s signature and dataMode routing are untouched; the English `languageDirective` change only appends the explicit script list the Hindi variant already carried (closing the v1 asymmetry note), leaving structure and the preserved `NO_DEV_INSTRUCTIONS_LINE` intact. No existing assertion was loosened beyond making the span end dynamic — the 217→221 delta is exactly the four new fix tests.
