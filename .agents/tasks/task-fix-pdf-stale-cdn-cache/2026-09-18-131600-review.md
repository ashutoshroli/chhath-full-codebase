# Distinct-key + cache-buster fix for the stale-CDN blank English report (v1)

The English Annual Report opened blank because generated PDFs were written to a fixed, timestamp-free R2 key (`keyForYear(year,'pdf',name,docType)`), so regeneration overwrote the same object at the same public URL and Cloudflare kept serving the previously-cached blank English bytes for up to four hours (`cf-cache-status: HIT`, `max-age=14400`). Hindi/Both were generated for the first time only after the earlier data fix, so they were never cached blank. The fix follows the codebase's own `keyForUserPhoto`/`keyForDonationQr` precedent: `keyForGeneratedPdf` embeds `Date.now()` so each regeneration lands at a distinct URL that no cache can hold stale, `putToR2` now writes a short revalidating `Cache-Control` on generated PDFs as defense in depth, the previous R2 object is best-effort deleted on regen to avoid orphan leaks, and the frontend appends a `?v=<token>` cache-buster on the links it opens.

Watch for: the previous-object delete runs *before* the `recordGeneratedFile` UPSERT commits in `convertDocxToPdf` and `applyPdfConvertResult`, so a DB write that fails after the delete leaves the row pointing at a just-deleted object — a dangling link, not a stale one (confirmed). A crash between `putToR2` and the UPSERT orphans the freshly-written object with no row to ever reclaim it (likely). Neither regresses the primary bug.

**Verdict**: APPROVED

## High-level view

The core mechanism is sound: distinct per-generation keys mean the URL Cloudflare cached blank simply no longer exists after regeneration, so the CDN cannot serve it. The `2026/pdf/<docType>/` prefix is preserved in the new key, and `keyFromR2Url` round-trips any key shape by stripping the public base, so both the "Move year to Drive" prefix listing and key derivation keep working unchanged. The public portal reads `generated_files.public_link`, which the UPSERT rewrites on every regen, so it always resolves the current object.

The `cacheControl` extension to `putToR2` is opt-in via a new fifth argument (or an options object); every existing non-PDF caller passes `contentType` only and is unaffected. Only the three generated-PDF write sites pass `GENERATED_PDF_CACHE_CONTROL`.

The delete-previous guards are correct for the cases they target: they never touch a legacy Drive-hosted `public_link` (`isR2Url` gate), never delete the object just written (old-key-differs check), and never fail generation (wrapped best-effort). The gap is ordering, not guarding: the delete fires before the DB row is rewritten, so a failed UPSERT downgrades a stale link into a dangling one. And no write site reclaims the new object if the process dies between the put and the UPSERT.

The tests are meaningful and prove-first: they drive the real `applyPdfConvertResult` twice and assert distinct URLs, old-key deletion, new-object retention, and that a Drive link is never deleted — all of which fail on baseline.

<details>
<summary>Issues (4)</summary>

1. **Delete-before-record dangling window** — in `convertDocxToPdf` and `applyPdfConvertResult` the old object is deleted before `recordGeneratedFile` commits; if the UPSERT fails, the row still points at the deleted object. Consider deleting only after the row is confirmed rewritten (as `moveOneUrl` already does for the archive path).
2. **Orphan on put-then-crash** — if the isolate dies between `putToR2` and the UPSERT, the new object is stored but never indexed, so nothing (not even the next regen's delete, which keys off the *row's* old link) will ever reclaim it. Acceptable given the 60s cache and the move-to-Drive prefix sweep, but worth noting as a bounded storage leak.
3. **Concurrent regeneration double-orphan** — two regenerations of the same record racing both read the same `existing` row, each write a distinct new key, and each delete the same old key; the earlier of the two new objects is orphaned (its row gets overwritten by the later UPSERT, and no delete targets it). Low likelihood, not blocking, no stale-content impact.
4. **Frontend token falls back to `f.id` for previously-generated links** — `withCacheBuster(f.public_link, f.generated_at || f.id)` uses a stable id when `generated_at` is absent, so the buster does not change across regens for such a row; the backend distinct key still prevents staleness, so this only weakens the redundant layer.

### Distinct key is what actually breaks the stale-CDN loop

`keyForGeneratedPdf(year, docType, fileName)` prepends `Date.now()` to the name segment while keeping the `<year>/pdf/<docType>/` prefix intact:

```
2026/pdf/report_en/1737000000000_Chhath-Puja-Report-2026.pdf
```

Because the URL Cloudflare cached blank (`.../report_en/Chhath-Puja-Report-2026.pdf`) no longer exists after regeneration, the edge has nothing stale to serve — the next request is a distinct URL and a guaranteed miss. This is the load-bearing part of the fix and it directly addresses the observed `cf-cache-status: HIT` on the old key (confirmed). The `GENERATED_PDF_CACHE_CONTROL = 'public, max-age=60, must-revalidate'` is secondary: it bounds how long even a fresh URL can be held, so a correction propagates in ~a minute rather than four hours (confirmed).

One thing the distinct-key scheme depends on: `Date.now()` has millisecond resolution, so two generations within the same millisecond collide on key. The two backend write sites are async-serialized per callback and the tests force a 3ms gap, so in practice this is not hit for a single record; a batch that regenerated the same record twice in under a millisecond is the only theoretical collision, and that is not a real flow (possible, not worth guarding).

### Move-to-Drive and public-portal contracts are preserved

`keyFromR2Url` derives the key by stripping the public base prefix, so it round-trips the new timestamped key exactly as it did the old fixed key — the `moveOneUrl` archive path and the `yearPrefix(year)` listing in `moveYearToDrive` both keep working because the new key still lives under `2026/`. `drive_path` is set to the new key at every write site, so the move feature finds the current object. The public portal (`generatedFilesByRecordIds` in `lookups.js`) selects `public_link` straight from `generated_files`, and the UPSERT rewrites `public_link` + `drive_path` on every regen, so readers always see the current object (confirmed).

### Delete-previous guards are correct; the ordering is the risk

`deletePreviousR2Object` reads the pre-UPSERT row's `public_link`, bails unless it `isR2Url`, derives the old key, and deletes only when `oldKey !== newKey`, all wrapped in try/catch + non-fatal `logErrorAt`. That correctly covers the three cases the task called out: a legacy Drive link is never passed to `deleteFromR2`, the just-written object is never deleted, and a delete failure never fails generation (confirmed, and the prove-first test pins the Drive-link case).

The unaddressed concern is *when* the delete runs relative to the DB write. In `convertDocxToPdf`:

```js
publicLink = await putToR2(env, key, ...);
drivePath = key;
await deletePreviousR2Object(env, existing, key, ...);   // old object gone here
// ... then, separately:
await recordGeneratedFile(env, docType, year, recordId, pdfName, publicLink, drivePath);
// ^ if this throws, the row still holds the OLD (now-deleted) public_link
```

`applyPdfConvertResult` has the same order (delete inside the `r2Available` block, `recordGeneratedFile` after). If the UPSERT fails, the row now points at an object that was just deleted — a broken link rather than a stale one. `moveOneUrl` already models the safe order for exactly this hazard (apply the DB change, verify it, *then* delete the source); the regen path deletes first. The blast radius is smaller than the archive path (the delete is best-effort and the primary bug is still fixed), so this is not blocking, but it is a real behavioral downgrade for a failing UPSERT (confirmed).

### Orphan-leak edges

Two leak windows survive the fix. First, a crash between `putToR2` and the UPSERT stores a new object that is never indexed; the next regeneration's delete keys off the *row's* old link, so it will never target the orphan (likely). Second, concurrent regenerations of the same record both read the same `existing`, both write distinct new keys, and both delete the same old key — the earlier new object becomes an orphan once the later UPSERT overwrites the row (likely, low frequency). Neither causes stale content, and both are bounded reclaimable by the move-to-Drive sweep only if they happen to be indexed; the pure put-then-crash orphan is not. These are acceptable trade-offs for a launch fix but should be tracked.

### Frontend cache-buster

`encodeURIComponent` on the token means a value containing `&`/`=` cannot inject a second query parameter (the test pins `a&b=c` -> `a%26b%3Dc`). The freshly-generated link uses `res.generated_at || Date.now()` (always changes); the "Already Generated" anchors use `f.generated_at || f.id`. The `f.id` fallback is stable across regens of the same row, so when `generated_at` is absent the buster does not vary — harmless because the backend distinct key already guarantees a new URL, but it means the frontend layer is a true redundancy only when `generated_at` is populated (confirmed).

### Tests

`r2-generated-pdf-key.test.mjs` pins distinctness across two calls, prefix preservation, the `Date.now()` name token, `keyForYear` non-regression, and that `cacheControl` is written for PDFs but not for the userPhoto/donationQr callers. `pdf-regen-stale-cdn.test.mjs` drives the real `applyPdfConvertResult` twice through the real UPSERT + delete path and asserts distinct URLs, both columns rewritten, old-key deletion, new-object retention, and the Drive-link-never-deleted guard. Both fail on baseline (timestamp-free key, contentType-only put), so they would fail if the fix were reverted — meaningful, not tautological.

Not tested: the delete-before-record dangling window (no test asserts row/object consistency when the UPSERT throws after the delete); the put-then-crash orphan; concurrent-regen orphan. These are the edges flagged above; adding a test that stubs `recordGeneratedFile` to throw and asserts the old object is still present would pin the ordering concern if it is addressed.
