# Display name in new-contribution push + opaque PWA shortcut icon (v1)

Two independently-reported bugs fixed in one branch. First, the new-contribution web-push notification printed the raw COLLECTIONS `Name` field — a `USER####` id code — instead of the contributor's display name; `push.js` now resolves the code through `userByIdCode` using the same fail-soft lookup pattern already used by `email.js` and `whatsapp.js`, falling back to the raw value only when unresolved. Second, the SvelteKit PWA's five app-shortcuts pointed at the transparent RGBA app icon, which Android's shortcut sheet renders as a blank white square; the shortcuts now point at a new opaque (color-type-2 RGB) 192×192 asset produced by a dependency-free generator script. Both fixes ship prove-first tests that fail if the change is reverted.

**Watch for:** the two fixes are unrelated and bundled in one branch (confirmed — flagged only for merge hygiene, not a defect); the id-code→name resolution depends on the USERS `id_code` column equaling the stored `ID` value, which is the same assumption email/whatsapp already rely on (confirmed consistent).

**Verdict**: APPROVED

## High-level view

The push fix extracts a pure, exported `composeNewContributionBody(env, payload)` helper that owns all body-string construction, resolves the id code to a name via `userByIdCode`, and keeps the log-and-swallow contract of `notifyNewContribution` intact — the caller in `index.js` is untouched. The extraction exists so the wording can be unit-tested without configured VAPID keys, since `broadcast()` no-ops when push is unconfigured. The name resolution mirrors `email.js:141` and `whatsapp.js:573`: look up, use `.Name` if found, otherwise fall back to the trimmed raw value, so an unresolved or blank code degrades to prior behavior rather than throwing.

The icon fix is a manifest-config change plus a committed binary asset. The root cause is correctly diagnosed: the app `icons` are transparent (color type 6) for launcher compositing, but the shortcut sheet draws icons as-is, so a transparent source produces a blank square. All five shortcuts now reference one opaque asset with `purpose: 'any'`; the app `icons` array legitimately still uses the transparent `icon-192.png` and was correctly left alone. The generator script decodes the existing RGBA icon and flattens it over the brand background into an RGB PNG with no external dependencies.

Both changes carry guard tests. The backend test asserts the resolved name appears and the raw code does not, across money / no-amount / blank-name branches. The frontend test verifies the shipped asset's PNG header is opaque and parses the shortcuts block of `vite.config.ts` to assert every entry points at the opaque asset and none at the transparent one.

### Name resolution fidelity and branch handling

`composeNewContributionBody` trims the payload's `Name`, and only calls `userByIdCode` when the code is non-empty, guarding against a lookup on `''`. The resolved name is `(contributor && contributor.Name.trim()) || code`, so three cases collapse cleanly: a resolved contributor yields the display name; an unresolved code yields the raw code (prior behavior, no regression); a blank name yields `''`, which the string builder then omits via the `name ?` guards. This is the same fail-soft shape as `email.js` and `whatsapp.js`, and matches the `userByIdCode` contract (returns `null`, never throws, when the row is absent).

The resolution correctness hinges on `usersByIdCodes` querying the `users` table by `id_code` but keying its result map by `u.ID`, then `userByIdCode` reading back by the same `id`. Per `tableRegistry.js` the `users` mapping is `'ID': 'id_code'`, so `.ID` and the `id_code` query key are the same value — the lookup resolves. The display name comes from `'Name': 'name'`. This is a pre-existing shared assumption (email/whatsapp already depend on it), not new risk introduced here.

The money-vs-material branch split is preserved verbatim from the old inline code: `Number.isFinite(amount) && amount > 0` picks the `₹{amount} by {name}` wording, everything else (zero, NaN, missing) uses the neutral `Naya contribution mila{: name}` form — so only the name source changed, no wording drift. The now-`async` helper stays inside the existing `try` in `notifyNewContribution`, so a lookup failure is still logged and swallowed rather than reaching the save path; the caller in `index.js` is unchanged (verified: empty diff).

### Opaque shortcut asset and the generator

The diagnosis is precise: app `icons` are transparent RGBA so the launcher composites them on its tile, but the shortcut sheet paints as-is, dropping transparent artwork against white. Verified on disk — `icon-192.png` is color type 6 and the new `icon-shortcut-192.png` is color type 2, both 192×192, bit depth 8, non-interlaced. `purpose: 'any'` is right for a plain (non-maskable) square. The transparent app icon is correctly retained in the `icons` array where compositing applies.

The generator is a self-contained PNG decode/re-encode: it inflates the RGBA IDAT, undoes the per-row filters (including Paeth), alpha-composites each pixel over the brand background `#F27A1A`, then re-encodes as filter-0 color-type-2 with a hand-rolled CRC32 and `IEND`. It asserts its input is 8-bit RGBA non-interlaced and throws otherwise, so a future re-run against a differently-encoded source fails loudly instead of emitting garbage. The committed PNG is the shipped artifact; the script is only needed to regenerate it.

### Test coverage

Backend: four cases exercise the changed code path directly — resolved money contribution (name present, raw code absent), unresolved code (raw fallback), no-amount material row (resolved name, no `₹`), and blank name with/without amount (neutral wording, no trailing `by`). These are genuinely prove-first: reverting to `payload.Name` breaks the `!body.includes('USER0001')` and exact-equality assertions. Ran locally: 4/4 pass.

Frontend: three cases — the shipped asset's IHDR is opaque type 2; the app icon is type 6 (documents *why* it can't back a shortcut); and the shortcuts block of `vite.config.ts` is regex-isolated so all five entries reference the opaque asset, none the transparent one, and each declares `purpose: 'any'`. The block-isolation regex correctly avoids the legitimate `icon-192.png` reference in the app `icons` array. Ran locally: 3/3 pass. The regex-parse approach is brittle to reformatting of the config, but it fails closed (a parse miss trips the `toBeTruthy` assertion) rather than silently passing.

**Not tested:** the generator script itself has no test (a one-off producing a committed artifact); no test asserts the built `manifest.webmanifest` output, though the briefing confirms a manual build verified all five shortcuts resolve to the opaque asset.
