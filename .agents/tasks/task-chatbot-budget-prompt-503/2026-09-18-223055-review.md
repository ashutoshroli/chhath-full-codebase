# Chatbot same-day lockout fix: shrink per-answer prompt, raise daily budget, surface the real 503/429 reason (review v1)

The public chatbot began replying "Sorry, something went wrong" for every visitor after roughly seven chats each UTC day. The whole-portal system prompt sent on every call cost ~28k tokens, so the 200,000-token/day default budget was spent in ~7 answers, after which the backend returned HTTP 503 for everyone until UTC midnight — and the frontend collapsed that 503 into the same generic error as a 502, hiding the real cause. The fix attacks both levers: `publicData.js` shrinks the GENERAL (no-year) summary prompt (SUMMARY_MAX_CHARS 6000→3500 plus narrower per-year/committee/contributor/loan/journey windows), `config.js` raises the `chatDailyTokenBudget` default to 2,000,000 (still env-overridable), and `Chatbot.svelte` now shows distinct messages for 503 and 429 while keeping the generic message for 502/network. Two new test files plus additions to `publicChat.test.mjs` pin the shrink, the budget, and the frontend status branch.

Watch for: the GENERAL path now shows only the most recent **3** years of totals/contributors/expenses/loans, down from 6 — a no-year question about a 4-year-old figure now silently omits that year and relies entirely on the user naming the year to hit the year-scoped path (confirmed). The 2,000,000 default is a fixed cost ceiling on an anonymous, money-costing endpoint with no alerting between "fine" and "hard 503 until midnight" (confirmed). Otherwise the cache-only contract, ID→name degradation, and PR#406 linkify path are intact.

**Verdict**: APPROVED

## High-level view

The root-cause fix is sound and the primary lever is the right one: the prompt shrink, not the budget bump, is what stops the endpoint from burning through its ceiling. With the 3500-char cap plus a ~512-token completion, per-answer cost drops from ~28k to a few thousand tokens, so the budget change is a safety margin rather than the fix itself.

The prompt shrink narrows the GENERAL path's recency window from 6 years to 3 across every section. This is a deliberate behavioral trade: a general "how much did we collect in <old year>" question no longer finds that year in the summary and depends on the year-scoped retrieval path, which triggers only when the question contains a bare 4-digit year. Relative phrases like "two years ago" are not resolved, so an older-year question phrased without a literal year will now come back thinner than before.

The budget default of 2,000,000 buys ~500 answers/day at the post-shrink cost versus ~7 before. It is a single global counter with no partial-degradation step and no operator signal before it trips; the failure mode is still a hard lockout for all visitors until UTC midnight, just much later. That is acceptable for launch but worth an operational note.

The frontend change is tightly scoped to the failure branch of `send()`. It prefers the server's own error string and falls back to localized `chat_limit`/`chat_busy`, keeping the generic `chat_error` for 502/network and for the `catch` path. The PR#406 timeout and linkify rendering are untouched.

Test coverage is real: reverting SUMMARY_MAX_CHARS and the budget default breaks four render tests, and reverting the frontend branch breaks the 503 test. The gap is that no test exercises a general question about a year that has now fallen outside the 3-year window (the behavioral edge the shrink introduces).

### The shrink is the fix; the budget is the margin

The 28k→few-thousand-token drop per answer comes entirely from `publicData.js`. SUMMARY_MAX_CHARS moving 6000→3500 caps the worst case, but the section-window reductions are what keep a data-rich portal from hitting that cap every call in the first place. The large-dataset test (12 years × 60 contributors/year × 20 committee/year) produces a summary ≤ 3600 chars, and reverting only SUMMARY_MAX_CHARS to 6000 breaks it — so the cap is genuinely load-bearing, not decorative. At ~4000 tokens/answer the raised budget serves 500+ answers versus ~7, which reframes the budget as a backstop rather than the primary lever. That ordering is correct: if the budget alone had been raised without the shrink, cost-per-answer would still scale with every added year of data.

### Narrowing the general window from 6 years to 3

Every recency-bounded section in the GENERAL (no-year) path went from `slice(0, 6)` to `slice(0, 3)`: per-year totals, top contributors, per-year expenses, and per-year loans; committee dropped `slice(0, 8)` → `slice(0, 3)` with a name-list cap of 8; the no-year committee fallback dropped 60 → 8. The stated rationale is that a no-year question is general and a user who wants an older year names it, hitting `buildYearScopedContext`. That holds only when the question contains a literal 4-digit year — `detectYears` matches `/\b(?:19|20)\d{2}\b/` and explicitly does not resolve relative phrases like "last year" or "two years ago." So a general question such as "how much did we collect four years ago" now finds neither the year in the summary (outside the 3-year window) nor a year-scoped match, and will answer more thinly than before the change. This is a real behavioral narrowing (confirmed by the slice edits and the `detectYears` implementation), not a regression in the crash sense, but it is the one place the shrink can quietly reduce answer quality.

### Cache-only contract and the nameOf/safeName asymmetry

The shrink introduces no new `fetch`/D1 access — the sole network path remains the pre-existing `getPortalData`/`getJson` cache load — and the per-person block, document-links block, resell note, guarantors, `NO_DEV_INSTRUCTIONS_LINE`, and year-scoped path are untouched. One asymmetry worth noting though it is pre-existing and not introduced here: the general path's top-contributors and committee lines resolve IDs with plain `nameOf`, while the year-scoped path uses `safeName` (which degrades an orphan `USER####` to "unknown member"). The diff changes only the slice sizes, not the resolver, so no new leak path is created; the inline comment documents the choice as intentional on the assumption that orphan contributor IDs are unlikely in that slice.

### Frontend failure branch

Fallback behavior worth pinning: when the server sends 503/429 without a parseable body, the localized `chat_limit`/`chat_busy` still surfaces (the `data.error` read is guarded), and the `catch`/network path stays on `chat_error`. The PR#406 anchor guard confirms a 200 answer with a URL still renders `<a target="_blank" rel~="noopener">`, and the AbortController/`CHAT_TIMEOUT_MS` timeout is untouched.

### Test coverage and what's not covered

`chatBudget.test.mjs` asserts the shipped default is 2,000,000, that 100 answers at ~4000 tokens stay under budget, that 500+ answers are affordable, and that `tokenBudgetExceeded()` trips exactly at `config.chatDailyTokenBudget` (asserted relative to config, not a literal, so an env override doesn't falsely fail). The `publicChat.test.mjs` additions pin the large-dataset cap (≤ 3600) while still matching a per-year totals line and a journey line, and confirm a year-scoped 2016 question (outside the 3-year window) still returns that year. Reverting SUMMARY_MAX_CHARS + budget breaks four render tests; reverting the frontend branch breaks the 503 test — so the guards bite.

Not tested: a **general** (no literal year) question whose answer year now falls outside the 3-year window. The year-scoped test proves 2016 works when named, but nothing asserts what happens when the same old year is asked about generally — which is precisely the behavior the shrink changes. A test asserting the older year is absent from `summarizePortalData(big, '')` yet present via the scoped path would lock in the intended trade-off and catch a future accidental widening or narrowing.

### Verification run

Render `npm test` = 228 pass / 0 fail. Frontend `npm run check` = 0/0, `npm test` = 311 pass / 0 fail, `npm run build` succeeds. Locally measured client JS = 668,237 bytes (under the 700,000 CI budget; the task notes cite 624,833, so the two measurements count different file sets — both pass, but the CI job's own measure is the authority).
