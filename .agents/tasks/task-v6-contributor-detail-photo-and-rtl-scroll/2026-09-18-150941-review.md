# Contributor-detail photo, clean detail-card anchoring, and live RTL rail across all v6 skins (v1)

The detail card in `Public/frontend-v6` now shows a contributor's profile photo (with an initials fallback), opens as a proper bounded/scrollable sheet instead of an unbounded one, and is reachable by tapping a contributor in every skin — not just premium. The photo decision is centralised in a new pure helper `shouldShowPhoto(photo, failed)` so the detail card matches the list-side pattern already used by `ContributorCard`/`ContributorsListModal`. The detail sheet was realigned to the `Modal.svelte` contract (`z-[60]`, `max-h`, internal `overflow-y-auto`). For the live right-to-left rail, aurora's hand-rolled manual `overflow-x` rail was replaced by the shared `LiveScroll` (the same auto-scroll marquee premium uses), and classic/festival/slate list rows were converted to buttons that open the shared detail card. classic/festival/slate have no horizontal rail by design, so nothing was made "live" there.

Watch for: the detail card now shares the exact same stacking level as the list modal (`z-[60]`), so when it opens on top of `ContributorsListModal` the ordering relies on DOM paint order rather than z-index (confirmed correct here, but fragile); the row/card buttons collapse their accessible name to just the contributor name via `aria-label`, dropping the amount/tags a screen reader would otherwise read (confirmed, consistent across skins); and aurora's rail restyle drops the old glass panel chrome, so its visual framing changes (likely intentional). Scope is clean — every change is inside `Public/frontend-v6` plus the expected `.agents/` task files.

**Verdict**: APPROVED

## High-level view

The photo logic is a shared fix. `ContributorDetail` is a shared component, so adding the `<img>`/initials branch there lights up the photo in every skin at once, and the decision is factored into `shouldShowPhoto` so the empty-string, null/undefined, and load-error cases behave identically to the list components. The failure flag is reset per contributor via an effect on `c.photo`, matching `ContributorCard`.

The detail-sheet fix is a straight adoption of the `Modal.svelte` layout contract: bounded height, a `shrink-0` header, and a `min-h-0 flex-1 overflow-y-auto` body, which is the standard remedy for the reported overflow/mis-anchoring. It moves from `z-50` to `z-[60]`, which is now equal to `Modal`, not above it — relevant because the detail card can open on top of the list modal.

Tap-to-open is routed through shared components where possible (`ContributorsListModal` rows, `LiveScroll` cards) and through per-skin buttons where not (classic/festival/slate list rows). Each skin mounts its own `ContributorDetail` bound to a local `selected` state. The nested case (detail over list modal) is handled correctly by `use:dialog` — the detail card inerts the list modal behind it and restores the already-locked scroll state on close.

The aurora rail swap is complete: the inline manual rail and all its now-unused imports/state were removed, and aurora now gets the identical auto-scroll + prev/pause/next + pause-on-interaction behaviour as premium because it renders the same `LiveScroll` with the same `onselect`/`oncountclick` contract.

### Photo/fallback parity with the list components

`shouldShowPhoto` returns `!!photo && !failed`, so an empty string, `null`, and `undefined` all fall to initials, and a load error flips `photoFailed` and falls back — the three cases the list components already handle. The `photoFailed` flag is reset by an effect on `c?.photo`, so recycling the card onto a different contributor (or the same key with a new URL) clears a stale failure, matching `ContributorCard`. `object-cover` is added to the `h-20 w-20 rounded-full` avatar so a non-square R2 image is cropped rather than distorted.

The failure store diverges from the list components deliberately: `ContributorsListModal` and the old aurora rail key failures in a `SvelteSet` by contributor key (many rows, one instance), whereas the detail card shows one contributor at a time and uses a single boolean reset on change — worth noting because the divergence means the two code paths can't share a regression test.

### Detail sheet realigned to the Modal contract

```
ContributorDetail (after)                 Modal.svelte
┌─ fixed inset-0 z-[60] backdrop ─┐        ┌─ fixed inset-0 z-[60] backdrop ─┐
│ ┌ surface flex flex-col ──────┐ │        │ ┌ surface flex flex-col ──────┐ │
│ │ max-h-[85vh]/sm:80vh        │ │        │ │ max-h-[85vh]/sm:80vh        │ │
│ │ overflow-hidden            │ │        │ │ overflow-hidden            │ │
│ │  ├ shrink-0 header (p-5)   │ │        │ │  ├ shrink-0 header         │ │
│ │  └ min-h-0 flex-1          │ │        │ │  └ min-h-0 flex-1          │ │
│ │     overflow-y-auto body   │ │        │ │     overflow-y-auto body   │ │
│ └────────────────────────────┘ │        │ └────────────────────────────┘ │
└─────────────────────────────────┘        └─────────────────────────────────┘
```

The old sheet had no `max-h` and no internal scroll region, so a tall card (a contributor with designation, father name, village, per-year breakdown, etc.) grew past the viewport with nothing to scroll — the most likely cause of the reported overflow/mis-anchoring. The header padding was split out (`p-5 pb-0` on the `shrink-0` header, `px-5 pb-5` on the scroll body) so the padding that used to live on the panel now sits correctly inside the two regions. `use:dialog` (focus trap, Esc, inert background, scroll-lock, focus return) is retained unchanged.

The move from `z-50` to `z-[60]` puts the detail card at the *same* level as `Modal`, not above it — and the detail card can open while `ContributorsListModal` (a `Modal`) is open. With equal z-index the winner is DOM paint order: `<ContributorDetail>` is mounted after `<Modal>`/`<ContributorsListModal>` in both the list modal and the skin pages, so it paints on top and its backdrop covers the list modal. Correct today, but order-dependent rather than declared; `z-[70]` on the detail card would make the intent explicit.

### Nested dialog behaviour (detail over list modal)

The interesting case is aurora/premium tapping a row inside `ContributorsListModal`, which mounts `ContributorDetail` on top of the modal that opened it. Both use `use:dialog`. When the detail card mounts, its `backgroundSiblings` walk stops at the top-level body subtree containing the detail node and marks every *other* top-level body child `inert` + `aria-hidden` — including the list modal's subtree — so focus-trap and the screen-reader tree are correctly confined to the detail card while it is on top. On close, the detail card removes `inert`/`aria-hidden` only from the elements it set them on, re-exposing the list modal.

Scroll-lock nests correctly by construction: the list modal sets `body.overflow = 'hidden'` and records the prior value; the detail card then records `'hidden'` as *its* prior value and restores `'hidden'` on close, leaving the lock in place until the list modal itself closes and restores the original. Focus return is guarded by an `isConnected`/containment check, so closing the detail card returns focus into the still-open list modal rather than stealing it.

### aurora rail swap to shared LiveScroll

aurora's inline rail was manual-only: a `no-scrollbar flex overflow-x-auto` container with no rAF, no `scrollLeft` drive, no prev/pause/next, and no live badge. It now renders `<LiveScroll onselect={onSelect} oncountclick={() => (listOpen = true)} />`, so aurora inherits the identical auto-scroll (rAF driving `scrollLeft`, seamless doubled-track loop), the prev/pause/next controls, and the pause-on-hover/touch/hidden/reduced-motion logic premium has. `onSelect` resolves the key to a `Ranked<Contributor>` from `rankedContributors(...)` exactly as premium does, and `oncountclick` opens the same `ContributorsListModal`. The swap is complete — the dead rail markup and its now-unused imports and state (`Crown`, `contributorTags`, `initials`, `avatarGradient`, `SvelteSet`, `failedPhotos`, `nameOf`, module-level `ranked`, `loading`, `lang`) were all removed, which is why `svelte-check --fail-on-warnings` stays clean.

One consequence worth flagging: the old aurora rail lived inside a `{GLASS}` panel with its own header and a "view list" link that showed even in the loading and empty states. `LiveScroll` provides its own `surface`-themed header, live badge, and controls, and its "view list" affordance renders only in the header (not during the skeleton). So aurora's rail framing changes visually — from the glass panel to the shared `surface` card — which is consistent with using one shared component but is a deliberate look change, not a pixel-for-pixel move. The `LiveScroll` header also duplicates a `role="list"` on the scroll track while wrapping each card in `role="listitem"`, and correctly marks the duplicated second copy `inert` + `aria-hidden` so keyboard/AT users don't traverse contributors twice.

### classic/festival/slate rows as buttons

Each of the three vertical-list skins turned its `<div>` row into a `<button type="button">` that sets `selected = entry` and mounts a per-skin `ContributorDetail`. The rows become keyboard-focusable and Enter/Space-activatable for free, and `w-full text-left` preserves the row layout. The only interactive-looking child is the `Crown` SVG (with an `aria-label`), which is not a focusable control, so there's no invalid nested-interactive-element problem. The search box and Contributors/Resold tabs are untouched, and the buttons live inside the same `{#each filtered}` block, so filtering/tab switching still drives which rows render.

The behavioral cost is the `aria-label={nameOf(entry.item)}` on each row button: an explicit `aria-label` overrides the button's computed name, so a screen reader announces only the contributor's name and drops the amount and material/service badges that the visible row (and the old `<div>`) exposed. It's consistent across all three skins and the list modal, so it's a uniform choice rather than a per-skin bug, but it does reduce what AT users hear compared to the sighted row. Dropping the `aria-label` (letting the button's text content form the name) or folding the amount into the label would restore parity.

### Test coverage

`ContributorDetail.test.ts` covers the photo/initials/error paths and the pure `shouldShowPhoto` truth table. `LiveScroll.test.ts` covers prev/next driving `scrollBy` with the right sign, the pause/play `aria-pressed` toggle, `onselect(key)` firing on a card click, and `oncountclick` on the view-list affordance — the contract every skin now depends on.

Not tested: the nested-dialog interaction (detail opening over the list modal — inert application, scroll-lock nesting, focus return into the list modal) is exercised by no test, and it's the most subtle behavior this change introduces. The per-skin row-button open path in classic/festival/slate (click sets `selected`, mounts the detail card) is also untested — the shared `ContributorDetail`/`shouldShowPhoto` tests cover the card itself but not the skin wiring that opens it. Neither gap is blocking given the shared components are tested, but a single test that opens the detail card from within `ContributorsListModal` would lock in the nested-dialog contract.
