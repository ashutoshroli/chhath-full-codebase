# Specificity fix for the two festival-skin dark themes' unreadable cards (v1 review)

The two festival-skin dark themes — `festival-dark` and `heritage-serif-dark` — were rendering light cream/stone body text on white cards on the Home contributor list. Root cause: their token blocks declared the intended dark opaque `--surface-bg` with a bare attribute selector `[data-theme='...']` (specificity 0,1,0), which lost to the generic `:root.dark { --surface-bg: 255 255 255 }` rule (0,2,0) because `<html>` carries both the `data-theme` attribute and the `dark` class at once. The fix raises exactly those two blocks to `:root[data-theme='...']` (0,2,0), so — being equal in specificity and later in source order — they win, restoring the dark card. A new source-scan guard test locks the selector shape and the dark-surface/light-ink pairing. No token values changed; no other theme block changed.

Watch for: the shared `ContributorDetail` modal (opened from the Home contributor list) uses the `.surface` class plus several unqualified text classes rather than festival tokens — its panel background now correctly resolves to the dark theme surface (improvement), but a few of its text values have no `dark:` variant. That behavior is pre-existing and identical on the already-shipping premium dark themes, so it is out of scope for this diff, but it is the one place the "is everything readable now" question does not fully close (possible).

**Verdict**: APPROVED

## High-level view

The specificity arithmetic in the code comments and the task diagnosis checks out: `:root.dark` and `:root[data-theme=...]` are both (0,2,0), so the tie breaks on source order, and the two theme blocks sit well below `:root.dark` in `app.css`, so they win and `--surface-bg` resolves to the dark maroon/charcoal value.

The scope is right, and this is the reason only two themes broke. Only `festival-dark` and `heritage-serif-dark` map to the festival skin among the dark themes, and the festival skin is the only one that paints an opaque card from `--surface-bg` (`fest.ts` `CARD = bg-[rgb(var(--surface-bg))]`). The other dark themes still inherit `:root.dark`'s white `--surface-bg`, but their skins render translucent `.surface` panels over a dark page rather than an opaque fill, so it never shows. The light festival themes and the `heritage-serif` serif-heading rule are untouched.

The Home contributor list — the surface named in the bug — is fully theme-token-driven (card `CARD`, names/village `--fest-ink`, amount `--fest-pos`, tags `--accent`/`--accent-2`), all declared inside the two blocks that now win, so that path is fixed.

The guard test is meaningful and was shown to fail 4/6 on revert. It is a source-scan, so it verifies the CSS *shape* rather than a browser-computed color. Its one blind spot: it asserts the good selector is *present*, not that a competing plain-attribute block is *absent*, so a re-introduced bare `[data-theme='festival-dark']` block later in source would not be caught.

The one open readability question is the `ContributorDetail` modal, which is a skin-agnostic overlay, not festival markup. It uses `.surface` for its panel (now dark, good) but styles its contributor name, father-name, detail, and count values with unqualified text classes that carry no `dark:` variant. This is unchanged by the diff and behaves the same on the existing premium dark themes, so it is out of scope here — flagged only because it is the reason the "everything is readable" claim cannot be fully closed from this change alone.

### Specificity reasoning holds, and the tie-break is the crux

`:root.dark` (line 24) sets `--surface-bg: 255 255 255` with specificity (0,2,0) — one pseudo/attribute-free class-equivalent (`.dark`) plus the `:root` type-level element counts as (0,2,0) here since `:root` is a pseudo-class. The two theme blocks were `[data-theme='festival-dark']` at (0,1,0), which is strictly lower, so `:root.dark` won and forced the surface to white while `--fest-ink` (declared only in the theme block, unaffected by `:root.dark`) stayed light. Rewriting them to `:root[data-theme='festival-dark']` makes them (0,2,0) — a tie with `:root.dark` — resolved by source order. Both theme blocks (lines 276 and 296) are far below `:root.dark` (line 24), so they win. The two `--surface-bg` values that now apply are `42 20 24` (avg 28.7) and `26 32 29` (avg 29), both firmly dark, paired with `--fest-ink` of `255 236 214` and `231 229 228`, both firmly light.

### Scope is correct — only the festival skin reads an opaque `--surface-bg`

```
skinMap.ts (dark themes):
  festival-dark        -> festival
  heritage-serif-dark  -> festival
  slate-dark           -> slate
  aurora, midnight...  -> aurora / premium

festival skin card (fest.ts):
  CARD = rounded-2xl border bg-[rgb(var(--surface-bg))] ...   <-- OPAQUE fill

shared panel (app.css .surface):
  background-color: rgb(var(--surface-bg) / var(--surface-alpha))  <-- alpha-blended
```

The festival skin is the only skin that paints an opaque background straight from `--surface-bg`, which is why only its two dark themes showed the white card. For the other dark themes, `:root.dark` still overrides `--surface-bg` to white, but their skins use the translucent `.surface` (at `--surface-alpha` 0.06 for the generic dark default) over a dark page, so white-at-low-alpha reads as a faint light film on dark — intended, not a regression. Leaving those blocks unchanged is the right call; touching them would have risked the opposite regression.

Every element the bug named on the contributor list resolves to a theme-local token declared inside the two blocks that now win: card `CARD` (`--surface-bg`), name and "times contributed" chip `--fest-ink`, village `--fest-ink`/0.6, amount `--fest-pos` (emerald-400 / emerald-300, picked to read on the dark cards), tags `--accent`/`--accent-2`.

### The `ContributorDetail` modal is the one loose end, and it is pre-existing

The modal opened from the contributor list is `$lib/components/ContributorDetail.svelte`, rendered as a skin-agnostic overlay from `+layout.svelte`, so it does not use festival tokens. Its panel is the `.surface` class:

```
.surface { background-color: rgb(var(--surface-bg) / var(--surface-alpha)); }
```

After the fix `--surface-bg` is the dark theme value and `--surface-alpha` is 0.8 / 0.85, so the modal panel is now a mostly-opaque dark surface — an improvement over the prior white. Most of its text carries explicit `dark:` variants (`text-slate-500 dark:text-slate-400`, `dark:text-brand-300`, `dark:text-amber-300`) that light up because `<html>` has the `dark` class. But the contributor name (`<p class="mt-3 text-lg font-black">`), the father-name and detail values (`font-semibold`), and the count (`font-bold`) have no color class at all and inherit the UA default `color`; neither the festival Shell, the premium Shell, nor `body` sets a base text color. On dark themes their legibility rides on `color-scheme: dark` (set by `:root.dark`) nudging the initial color light, which is engine-dependent. This is unchanged by the diff and behaves identically on the shipping premium dark themes (warm-night, midnight) that also open this modal, so it is out of scope per "review only what changed" — but it is why a live pass on the modal specifically is worth doing after deploy.

### Test coverage

Covered: the presence of the `:root[data-theme=...]` selector for both ids; the dark-surface (< 128 avg) / light-ink (> 128 avg) pairing for both; and that the `app.html` no-flash `DARK` map lists both ids so the `dark` class is actually applied (without which the whole specificity interaction wouldn't fire). The revert-fails-4/6 check confirms the assertions bite.

Not tested: that no competing bare `[data-theme='festival-dark']`/`[data-theme='heritage-serif-dark']` block reappears later in source (the assertion is presence-only, so a regression that re-adds the low-specificity block alongside the new one would still pass); the actual browser-computed cascade winner (acknowledged as verified manually during diagnosis, not automatable here); and the `ContributorDetail` modal's rendering on these themes.
