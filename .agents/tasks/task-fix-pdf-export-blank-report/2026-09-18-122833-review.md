# PDF Export blank Annual Report: forward `req.data` on the bulk dispatch path (v1)

The management portal's More → PDF Export produced an Annual Report PDF with the right template layout but no data — every table showed its empty-state fallback ("No contributors." etc.) and every summary scalar rendered blank. Root cause: the `convertDocxToPdfBulk` handler in `mgmt/backend/src/index.js` forwarded `req.base64` as the 5th argument of `docx.dispatchBulkPdfConvert(...)`, but that parameter is `data` (the placeholder set) and the frontend posts the placeholders under `req.data`. `req.base64` is undefined on this path, so Render received `data: {}` and docxtemplater collapsed every loop to its inverted fallback. The fix changes that single argument to `req.data` and adds an explanatory comment; the sibling `convertDocxToPdf` (single/consent) handler and the frontend were left untouched by design. Three new tests were added: a source-level wiring contract, a behavioral dispatch test, and a Render fill test.

Watch for: nothing blocking. The one-line fix matches the dispatch contract and the frontend payload (confirmed). The behavioral dispatch test is revert-insensitive by design — the source-level wiring test is the actual revert guard, and it does fail on `req.base64` (confirmed via its own control). One nearby stale comment (batch `items` shape) is pre-existing and out of scope.

**Verdict**: APPROVED

## High-level view

The fix is a single positional-argument correction bound by a clear contract: `dispatchBulkPdfConvert(env, docType, year, recordId, data, fileName, user, opts)` forwards its `data` parameter to Render as `data: data || {}`, and the frontend `api.js convertDocxToPdfBulk` sends the placeholder set under the `data` key. Aligning the handler to `req.data` closes the gap that sent `{}` to Render.

The scoping is correct. `convertDocxToPdf` (staff single-record / consent) genuinely posts a pre-filled `.docx` via `req.base64` and is rightly unchanged; the batch path (`convertDocxToPdfBatch` → `dispatchBulkPdfBatch`) already reads each item's `.data`, which is why receipts were never affected. Note the same bulk handler also backs ReceiptModal, DownloadCenter, and PdfExport — all four bulk single-record callers pass placeholders positionally as `data`, so the fix repairs them all, not just PDF Export.

Test coverage is layered and non-superficial. The source-level test parses both call sites and asserts the handler's 5th dispatch arg is exactly `req.data` (failing on any revert to `req.base64`); the behavioral test drives the real `dispatchBulkPdfConvert` and deep-equals the outbound Render payload's `data` against a PdfExport-shaped placeholder object; the Render test builds a real `.docx` and proves non-empty arrays render rows while `[]`/`{}` render the fallback. Validation is host-based (node:test with D1/KV stubs); the live Worker→Render→Drive path is not exercised, a known environment constraint rather than a coverage gap.

### The dispatch contract and the one-line fix

`dispatchBulkPdfConvert` in `docxTemplates.js` takes `data` as its 5th positional parameter and forwards it into the Render `pdf_convert` job as `data: data || {}`. The frontend sends the placeholder set under `data`:

```
api.js:  call('convertDocxToPdfBulk', { docType, year, recordId, data, fileName, force })
```

so `req.data` is the placeholder set and `req.base64` is undefined on this path. The `|| {}` default in `dispatchBulkPdfConvert` is what turned the undefined into the empty object that Render filled — a fail-quiet default that produced a plausible-looking but dataless PDF rather than an error. The fix (`req.base64` → `req.data`) is the minimal correct change; the added comment documents that this path sends fill *data*, not a pre-filled `.docx`, which is the distinction that was lost.

### Scoping: what was correctly left alone

```
convertDocxToPdf       -> req.base64  (pre-filled .docx; consent/single)   UNCHANGED — correct
convertDocxToPdfBulk   -> req.data    (placeholder set; Render fills)       FIXED
convertDocxToPdfBatch  -> req.items[].data (per-record placeholders)        UNCHANGED — correct
```

`convertDocxToPdf` really does ship a filled `.docx` as base64, so keeping `req.base64` there is right, and the wiring test pins this so a future "consistency" refactor can't accidentally switch it to `data`. `dispatchBulkPdfBatch` reads `it.data` per item (`const data = (it && it.data && typeof it.data === 'object') ? it.data : {}`), matching the frontend's `items:[{recordId, data, fileName}]` — this is why receipts, which use the batch path, never went blank. The blast radius is the four bulk single-record callers; all pass placeholders as the `data` positional, so all four are fixed uniformly.

### Test meaningfulness

The source-level wiring test (`pdf-export-bulk-data-wiring.test.mjs`) is the revert guard. It extracts the `dispatchBulkPdfConvert(...)` argument list from `index.js`, splits on top-level commas, and asserts `args[4] === 'req.data'` and `!== 'req.base64'`. It also includes a self-check that both extractors found real, non-empty text (guarding against a vacuous pass) and a control that runs the same positional check against a hand-written reverted call and asserts it throws. This test fails on `main` and on any revert — it is the assertion that would have caught the bug.

The behavioral test (`pdf-export-report-data.test.mjs`) calls the real `dispatchBulkPdfConvert` below the handler with a PdfExport-shaped placeholder object, stubs `globalThis.fetch` to capture the outbound Render job, and deep-equals `payload.data` against the input — verifying arrays arrive as arrays with all rows and nested field names intact, plus a control pinning the `{}` symptom. Because it calls the dispatch function directly rather than through the handler, it does not exercise the `req.data` vs `req.base64` selection and so would still pass on `main` — this is acknowledged in the briefing and is fine given the wiring test carries the revert-sensitivity.

The Render test (`report-loops-fill.test.mjs`) builds a minimal real `.docx` with PizZip containing a `{#contributors}...{/contributors}` loop plus a `{^contributors}` fallback and runs the actual `fillDocxTemplateFromBase64`/`FromBytes`, asserting a non-empty array yields one row per entry with no fallback, and that `[]` and `{}` both render the empty-state fallback with no rows — proving `{}` is what produced the observed symptom.

All three run green on host (backend 7 new pass, Render 4 new pass). Live Worker→Render→Drive is not exercised (no Cloudflare/Render creds) — a stated environment constraint.
