# List Management ADD silently lost data — meta.changes guard + live id-column rebuild (v1)

The management portal's List Management section (Category / Payment Mode / Loan Status / Village) reported `{success:true}` on ADD while the new row never persisted, whereas EDIT worked. The change hardens the three write handlers in `mgmt/backend/src/dropdownLists.js` to inspect `result.meta.changes` and throw a `ValidationError` when a write changes zero rows — following the pattern already established across the codebase (`announcements.js`, `templates.js:162`, `docxTemplates.js:212`, `loans.js`). It also ships an operator runbook + SQL that rebuilds the live `dropdown_lists` table to restore `id INTEGER PRIMARY KEY AUTOINCREMENT`, since the true live root cause (a drifted `id` column storing NULLs) is a shape corruption the `meta.changes` guard alone cannot catch. A prove-first test suite and an operator-SQL validation test accompany the code.

Watch for: the `meta.changes` guard does **not** catch the exact live fingerprint (plain `id INTEGER` → INSERT reports `changes=1` while storing `id=NULL`) — the guard and the SQL rebuild are two independent halves and only the pair fully resolves the bug (confirmed). The fix depends on the `withAuth`/dispatch layer turning the thrown `ValidationError` into an HTTP 400, which it does (confirmed).

**Verdict**: APPROVED

## High-level view

The behavioral fix is a three-line-per-handler guard: capture the `.run()` result and throw `ValidationError` when `!res.meta.changes`. Add surfaces "Could not add the item. Please try again."; update and delete surface "Item not found." The guard is intentionally more defensive than the codebase norm (`!res || !res.meta || !res.meta.changes` vs the established bare `!result.meta.changes`), which is harmless but slightly inconsistent. The legitimate no-field-update no-op (`if (!sets.length) return {success:true}`) is preserved and returns before the guard, so a caller passing no editable fields still gets a success without a spurious "Item not found."

The guard's honest limit is documented in the code and tests: it converts the broad class of 0-change writes into visible errors, but the specific live failure — a table whose `id` lost `PRIMARY KEY AUTOINCREMENT` — produces a `changes=1` INSERT with a NULL id, which the guard cannot distinguish from a real write. That variant is fixed only by the operator SQL.

The operator SQL is a standalone cleanup (deliberately not a numbered migration, to avoid the `h10-m38` DROP/ALTER guard) that rebuilds the table via the codebase's documented CREATE-new / INSERT-SELECT / DROP / RENAME / recreate-indexes recipe, carrying every row and id forward and recreating both indexes. It matches `mgmt/db/schema/core.sql` exactly. The runbook gates the destructive rebuild behind a backup, a read-only pre-flight detection that stops if `id` already has `PRIMARY KEY`, a row-count before/after check, and a UI verification, and warns that a fresh DB is already correct and must not run it.

Test coverage is strong: the write-handler suite is prove-first (4 tests fail if the src change is reverted — verified), exercises persistence against the real committed schema, and pins the NULL-id limitation as documented behavior rather than a surprise. The SQL test applies the actual script file through `node:sqlite` and asserts the end-state shape, row/id preservation, and re-enabled autoincrement.

### meta.changes guard and the error messages

Each of the three handlers now captures the `.run()` result and rejects a zero-change write:

```js
const res = await env.DB_CORE.prepare('INSERT ...').bind(...).run();
if (!res || !res.meta || !res.meta.changes) throw ValidationError('Could not add the item. Please try again.');
```

Add uses a retry-oriented message; update and delete use "Item not found." — the messages match the sibling modules. The distinction matters: a 0-change UPDATE/DELETE against a keyed row means the id doesn't exist, while a 0-change INSERT is an infrastructure-level no-op the user can only retry.

The guard predicate is `!res || !res.meta || !res.meta.changes`, more defensive than the established bare `!result.meta.changes` used everywhere else — a small stylistic divergence from the pattern the change claims to follow. Low priority.

The dispatch path makes the guard user-visible: `index.js` routes each action through `withAuth`, and `httpStatusForError` maps a `ValidationError` (`expected===true`, `authError===false`, no `permission` flag) to HTTP 400 with the message in the body — so the previously-silent ADD now returns `success:false` with a readable message. The no-field-update no-op (`if (!sets.length) return {success:true}`) returns before this guard, so a no-field edit does not falsely raise "Item not found."; the test `a no-field update is a legitimate no-op...` pins it.

### Why meta.changes can't catch the live fingerprint

The guard defends against writes that report `changes=0`. The live table's actual failure is different: `id` drifted from `INTEGER PRIMARY KEY AUTOINCREMENT` to a plain `id INTEGER` (via the reset RUNBOOK's `wrangler d1 export` + restore path, which re-emits the column without AUTOINCREMENT). Against that shape, an INSERT omitting `id` reports `changes=1` and stores `id=NULL` — a "successful" write of an unusable row. The guard sees `changes=1` and passes it through. This limitation is explicitly documented in both the SQL header and the `drifted plain-id INTEGER stores a NULL id` test, so it's surfaced rather than hidden. The durable fix for this is the SQL rebuild, not the code.

### Operator SQL rebuild — the atomicity soft spot

```
CREATE dropdown_lists_new (id INTEGER PRIMARY KEY AUTOINCREMENT, ...)
INSERT INTO dropdown_lists_new (...) SELECT ... FROM dropdown_lists   -- ids carried forward
DROP TABLE dropdown_lists
ALTER TABLE dropdown_lists_new RENAME TO dropdown_lists
CREATE INDEX idx_dropdown_lists_list_type ...
CREATE INDEX idx_dropdown_lists_active ...
```

The soft spot is the atomicity claim. The header and runbook state all statements "share one implicit transaction" so "the whole rebuild lands or none of it does." There is no explicit `BEGIN`/`COMMIT` in the file — atomicity depends entirely on how `wrangler d1 execute --file` batches statements. A partial failure after `DROP TABLE dropdown_lists` without a rollback would leave the table gone. An explicit transaction wrapper would make the guarantee independent of tooling. Not blocking given the mandatory step-0 backup, but worth hardening.

### Test quality

The write-handler suite (`dropdown-list-writes.test.mjs`) is genuinely prove-first: reverting `dropdownLists.js` to `main` fails exactly the 4 drift-guard / not-found tests and passes the rest (verified by stashing the src change). It tests real persistence against `schemaFor('core.sql')` (asserting a non-null positive `__rowIndex`), sort_order max+1 sequencing, the case-insensitive duplicate rejection, the no-field no-op, and pins the NULL-id live fingerprint as documented behavior. The drift-guard uses an INSTEAD OF trigger view to force `changes=0`, which is a faithful model of a silent no-op write and matches D1's `meta.changes` semantics through the `node:sqlite` stub.

The SQL suite (`dropdown-lists-id-fix.test.mjs`) reads the actual `.sql` file and applies it through `node:sqlite`, asserting the drift precondition, the restored `PRIMARY KEY`/AUTOINCREMENT DDL, row and id survival, a fresh autoincrement INSERT, and both indexes. It lives in `test/` on purpose so the migration guards don't scan it.

Not tested (acceptable, given the agent can't touch live D1): the real `wrangler d1 execute --file` transaction wrapping (the atomicity claim above is asserted, not exercised), and the end-to-end UI ADD-reload path (covered manually in runbook step 4).
